# Оператор читает логи машины, а не только правит её

## Why

**Учётная запись оператора не может прочитать ни одного лога nginx**, и это обнаружилось,
когда понадобилось. Замер на `busel` 2026-08-23:

```
id km  →  uid=1000(km) gid=1000(km) groups=1000(km),27(sudo)
ls -la /var/log/nginx/  →  -rw-r----- 1 www-data adm
sudo -u km head -1 …    →  Permission denied
```

Роль заводит оператора в `sudo` и на этом останавливается. Пока машину только настраивали,
этого хватало: правки идут через `sudo`, а логи читал человек за приглашением — тоже через
`sudo`. Но работы по расписанию идут **под самим оператором**, без `sudo`, и с этого момента
недостающая группа перестала быть неудобством.

**Отказ при этом тихий и опаснее обычного.** Нечитаемый файл отдаёт ноль строк, а ноль строк
у читателя логов означает «никто не приходил». То есть отсутствие прав записывается как
факт о поведении краулеров — каждую ночь, с кодом возврата 0. Читатель, который заводится
ровно затем, чтобы поймать молчание, сам начинает молчать в точности так же.

## What Changes

- **`bootstrap_user_groups`** — новая переменная, по умолчанию `[sudo, adm]`. Прежний
  жёстко зашитый `groups: sudo` заменяется ею.
- **`adm` в умолчании, а не только у busel.** Группа даёт чтение `/var/log`, и это свойство
  оператора как такового: машина, где оператор правит конфигурацию, но не может прочитать
  журнал её работы, настроена наполовину. Читать логи будут не только реципиенты.

## Почему группа, а не `sudo cat`

Разбирать чужой ввод и иметь права root — разные вещи, и совмещать их без нужды не стоит.
Чтение лога не требует root вовсе: файл открыт группе `adm` именно для этого. `sudo` в
команде дал бы работе полномочия администратора там, где нужна одна операция чтения.

## Impact

- `roles/bootstrap/defaults/main.yml` — переменная
- `roles/bootstrap/tasks/main.yml` — вместо литерала
- `molecule/bootstrap/` — сценария у роли не было; заводится вместе с правкой
