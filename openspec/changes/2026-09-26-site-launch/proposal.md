# Запуск сайта ролями krot: от регистратора до sitemap, принятого поисковиками

## Почему

Запуск сайта сейчас живёт в двух местах: busel ведёт его своими командами
(`src/Colony/{Launch,Registrar,Cloudflare,Search}`), gudok повторяет те же шаги своими. Грабли,
найденные в одном проекте, в другой не переезжают — их переоткрывают. Каждая стоила сайта или
часов:

- без токена Cloudflare запуск busel/tsbelgie успел создать зону, сертификат и базу, а упал
  только на поиске — нет общего чтения состояния до первой записи;
- dry-run busel чуть не создал зону — check-mode не был гарантией;
- roksasex.pl отдал поисковику sitemap с 401, и Google за час пометил отправку ошибкой;
- stadtdame резал сутки в GA4 по Europe/Minsk вместо страны сайта.

Решение владельца: инструмент один — Ansible, роли и модули лежат в `haspadar.krot`, ими
пользуются busel, gudok и следующие проекты. План согласован между сессиями gudok и busel
2026-09-26.

### Это переоткрывает два решения krot

1. **«Роль знает про хост, но не про приложения на нём»**
   (`wiki/domains/collection-layout.md`, `openspec/ARCHITECTURE.md`, `README.md`). Роли
   `site_*` знают домен, зону и базу сайта — то, что таблица слоёв отдавала «провижинингу сайта в
   busel». Принцип сохраняется в другой форме: **роли машины** по-прежнему не знают про сайты;
   **роли сайта** знают один сайт — тот, что передан переменными `site_*`, — но не знают, **чей**
   он: ни имени проекта, ни его конфига, ни его команд. Всё проектное подключается task-файлами
   проекта (наполнение, деплой, открытие, запись полученных ID).

2. **«Terraform — не про сервер»** (`collection-layout.md`): «CF-зоны и DNS, домены Dynadot»
   отданы будущему Terraform, «смешивать их в одном репозитории значит потерять границу».
   Terraform так и не появился, а запуск нуждается в порядке шагов, который декларативное
   состояние не выражает: зона → ожидание active → NS у регистратора → записи только после
   делегирования → сертификат до деплоя. Граница переносится: не «облако против сервера», а
   **роли машины против ролей сайта**, в одной коллекции, разными наборами.

Оба пересмотра подтверждены владельцем 2026-09-26.

## Что меняется

### Модули (`plugins/modules/`, Python)

Готовых модулей для Dynadot, зон/настроек/Origin CA Cloudflare, Umami, GA4, UptimeRobot, GSC,
Яндекса и Bing нет — пишем свои: `dynadot_ns`, `cloudflare_zone`, `cloudflare_zone_settings`,
`cloudflare_origin_cert`, `umami_website`, `ga4_property`, `uptimerobot_monitor`, `gsc_site`,
`yandex_site`, `bing_site`. Готовые берём: `community.general.cloudflare_dns` (записи, в том
числе TXT/CNAME подтверждения поисковиков) и lookup `community.general.bitwarden` (секреты).

Общее для всех модулей:

- **check-mode без побочных эффектов** — ни одного пишущего запроса;
- **get-or-create**: сущность ищется по домену до POST, повторный вызов — `changed=false`;
- **«не смог спросить» ≠ «нет»**: сбой запроса или пустой ответ резолвера — отказ, а не
  «отсутствует»;
- **успех проверяется повторным чтением**, а не кодом ответа на запись;
- **адрес API — параметр** с боевым значением по умолчанию: так молекула направляет модуль в
  подделку, не трогая код.

Грабли по каждому API — в `design.md`, они часть требования, а не заметки.

### Роли (в порядке плейбука)

1. `site_preflight` — только чтение и assert: SSH до машины, переменные заданы, секреты
   находятся, в `shared/.env.local` есть переменные из списка проекта (имена, не значения).
   Собирает состояние всех следующих шагов: done / pending / blocked. Blocked — запуск стоит до
   первой записи.
2. `site_domain` — NS у регистратора (`dynadot_ns`).
3. `site_dns` — зона, настройки, apex и www proxied A. Записи — только когда зона active **и**
   публичные резолверы видят NS Cloudflare.
4. `site_tls` — Origin CA на машину до первого деплоя.
5. `site_database` (опц.) — база сайта от роли сайта.
6. *шаг проекта: наполнение* (`site_project_fill`).
7. `site_analytics` — Umami, опционально GA4; ID уходят фактом `site_launch_results`.
8. *шаг проекта: деплой* (`site_project_deploy`), затем `site_serve_check`.
9. *шаг проекта: открытие* (`site_project_open`).
10. `site_monitor` (опц.) — UptimeRobot.
11. `site_search` — sitemap 200 без авторизации, затем GSC / Яндекс / Bing по списку.
12. `site_check` — финальный смоук; блокеры валят запуск, предупреждения — нет.

Длинное ожидание (активация зоны: минуты–сутки) внутри play не делается: шаг кончается понятным
сообщением «ждём active, перезапустите», а повторный прогон продолжает с того же места.

### Что остаётся проекту

Вёрстка, тексты, наполнение, деплой, открытие сайта и запись полученных ID туда, откуда их
читает приложение (`site_results_writer`). Где проект держит переменные `site_*` — решает
проект; условие одно: у значения один источник.

### Приёмка

Прогон на уже живом `tbl-telefon.de` (gudok): сначала `--check`, затем обычный. Все шаги — ok,
`changed=0`, ничего не создано повторно. Живой прогон — только с подтверждения владельца.

## Вне этого change

- Переход busel и gudok на роли — работа в самих проектах.
- Где проекты хранят инфраструктурные переменные сайта.
- Заведение отдельных аккаунтов Cloudflare под gudok: роль лишь позволяет указать аккаунт.
