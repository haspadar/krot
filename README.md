# Krot

Ansible-коллекция `haspadar.krot` — переносимые роли для провижининга Ubuntu-машин.
Крот роет под сервисами и чинит «подземку» незаметно — отсюда имя.

Роли знают про **хост**, но не про приложения на нём: специфика проекта живёт в его
`inventory`/`group_vars`, а не внутри роли.

## Установка

```yaml
# requirements.yml в проекте
collections:
  - name: git+https://github.com/haspadar/krot.git
    type: git
    version: main   # или тег, чтобы заморозить инфраструктуру
```

```bash
ansible-galaxy collection install -r requirements.yml
```

Зависимости (`ansible.posix`, `community.general`, `community.postgresql`) подтягиваются сами.

## Использование

```yaml
- name: Provision the machine
  hosts: web
  roles:
    - role: haspadar.krot.common
    - role: haspadar.krot.php
    - role: haspadar.krot.nginx
    - role: haspadar.krot.firewall
    - role: haspadar.krot.fail2ban
```

Голая машина — сперва один раз под root:

```yaml
- name: Bootstrap SSH access
  hosts: new
  roles:
    - role: haspadar.krot.bootstrap
      vars:
        bootstrap_authorized_keys: ["ssh-ed25519 AAAA..."]
```

```bash
ansible-playbook bootstrap.yml -u root -k
```

## Роли

| Роль | Что делает |
|------|-----------|
| `bootstrap` | Операторский юзер + sudo, `authorized_keys`, `PermitRootLogin no`, `PasswordAuthentication no` |
| `common` | hostname, timezone, базовые пакеты (включая `btop`, `ncdu`, `ripgrep`, `jq`), unattended security-upgrades |
| `firewall` | ufw; при `firewall_cloudflare_only` пускает 80/443 только с диапазонов Cloudflare и обновляет их weekly-таймером |
| `fail2ban` | fail2ban с джейлом `sshd` |
| `php` | PHP-FPM из ondrej PPA; slowlog, access-log с таймингами |
| `postgresql` | PostgreSQL из pgdg, csvlog со slow-query логом, `pg_stat_statements`. Только сервер, без баз |
| `nginx` | nginx.conf, права, ротация, basic auth. Per-site vhost'ы, log_format и real-IP не трогает |
| `docker` | Docker + compose-плагин, лимит на рост логов контейнеров |
| `deploy_keys` | Отдельный SSH-ключ на каждый приватный репозиторий + host-алиасы, чтобы git предъявлял нужный |
| `deploy` | Запускает Deployer проекта с control-машины. Релизы и rollback остаются в `deploy.php` |
| `goaccess` | Отчёты посещаемости по логам nginx — полный и «только люди» на каждый сайт |
| `geoip` | Базы MaxMind GeoLite2, обновляются таймером. Нужна ролям, которым надо сопоставить адрес со страной |

Каждая роль атомарна и применима отдельно. Все параметры — в `roles/<role>/defaults/main.yml`.

**`fd` на машине называется `fdfind`.** Пакет `fd-find` не может занять имя `fd` — оно
принадлежит другому пакету Debian. Алиас роль не заводит: содержимое login-шелла — дело
оператора, а не машины.

### Что роли намеренно НЕ делают

- **vhost'ы конкретных сайтов** — их генерит сам проект; роль `nginx` владеет только каталогами
  `sites-available`/`sites-enabled` и их правами.
- **Базы конкретных приложений** — роль `postgresql` ставит только сервер.
- **Выкатку кода** — это Deployer/CI проекта. Пересечение одно: роль создаёт юзера и каталог
  с правами, куда потом кладутся релизы.

## Деплой

Роль `deploy` — тонкая обёртка: Deployer запускается **на control-машине** и сам ходит на сервер
по SSH. CI для выкатки не нужен, это ручной путь.

```bash
ansible-playbook deploy.yml
ansible-playbook deploy.yml -e deploy_task=rollback
ansible-playbook deploy.yml -e deploy_branch=some-branch
```

Роль намеренно не переизобретает релизы, symlink и rollback — этим уже занимается `deploy.php`
проекта.

**Два подводных камня, оба реальные:**

- **Один deploy key нельзя использовать в двух репозиториях GitHub.** Машина, тянущая несколько
  приватных репо, получает по ключу на каждый (`deploy_keys`) плюс host-алиас: клонировать надо
  с `git@<name>.github.com:owner/repo.git`. Без алиаса ssh предъявляет первый подошедший ключ,
  и GitHub отвечает за чужой репозиторий.
- **`log_format` и real-IP роль не пишет** — их владелец генератор vhost'ов проекта: он знает,
  какое имя формата называют его же конфиги, и обновляет CF-диапазоны при каждой генерации, а не
  раз в прогон Ansible. Два писателя на одну настройку неизбежно разъезжаются, а устаревший
  `set_real_ip_from` молча пишет в логи адрес CDN вместо посетителя.

## Закрытие неопубликованных сайтов

Сайт не должен быть доступен, проиндексирован или обойдён краулером, пока его не посмотрели.
Поэтому **закрытое состояние — умолчание**, а публикация — явное действие.

Krot ставит только механизм: файл паролей `/etc/nginx/.htpasswd` (пароль берётся из секретницы
в рантайме) и сниппет:

```nginx
# /etc/nginx/snippets/krot-auth.conf
auth_basic "Preview";
auth_basic_user_file /etc/nginx/.htpasswd;
```

**Какие сайты закрыты — решает не Krot, а генератор vhost'ов проекта.** Он добавляет в шаблон
одну строку, пока сайт не помечен опубликованным:

```nginx
server {
    server_name {{ domain }};
{% raw %}{% if not published %}{% endraw %}
    include /etc/nginx/snippets/krot-auth.conf;
{% raw %}{% endif %}{% endraw %}
    ...
```

Так сайты открываются по одному, а не все разом. Включается через `nginx_auth_enabled: true`
плюс `nginx_auth_password` из секретницы.

## Cloudflare-замок

`firewall_cloudflare_only: true` закрывает 80/443 для всего, кроме опубликованных диапазонов
Cloudflare, — origin-адрес перестаёт отвечать напрямую.

Диапазоны берутся с `cloudflare.com/ips-v4`/`ips-v6`, складываются в
`/etc/krot/cloudflare-ranges.txt` и обновляются юнитом `krot-cf-ranges.timer` (еженедельно).
Роль `nginx` этот список не читает: real-IP настраивает генератор vhost'ов проекта, обновляя
диапазоны при каждой генерации.

Скрипт `/usr/local/sbin/krot-cf-ranges` отказывается менять правила, если ответ CF пустой или
подозрительно короткий: усечённый список молча отрезал бы сайты от мира.

**Про SSH:** правило для 22 порта создаётся до включения ufw и до CF-замка, поэтому доступ
к машине не теряется. Роль `bootstrap` по той же причине отказывается выключать парольный вход,
пока не убедится, что валидный ключ на месте.

## Логи

Настроены под сбор (Loki/Alloy и аналоги), но агент не ставится — это отдельная роль.

- **nginx** — формат задаёт генератор vhost'ов проекта; роль отвечает за ротацию и за то, что
  `conf.d` подключается раньше vhost'ов, которые на него опираются.
- **php-fpm** — `/var/log/php/`: access с таймингами, slowlog со стек-трейсом медленных
  запросов, отдельный error-log.
- **postgresql** — csvlog, медленные запросы, `log_lock_waits`, `log_checkpoints`, плюс
  `pg_stat_statements` (см. ниже).

nginx и php ротируются через logrotate, PostgreSQL ротирует себя сам.

## Мажорная версия PostgreSQL

`postgresql_version` — это версия, которую роль ставит, а **не** обновление уже работающей.
PostgreSQL не читает каталог данных предыдущей мажорной версии: поднятие переменной с 16 на 18
ставит **второй кластер рядом**, а не апгрейдит первый.

Дальше происходит незаметное: `pg_createcluster` берёт первый порт, не занятый существующим
кластером, то есть 5433,
а конфиг роли объявляет 5432 — новый кластер не стартует, приложение продолжает работать со
старым, и всё выглядит исправным. Поэтому роль **отказывается** прогоняться рядом с кластером
чужой версии и называет причину.

Порядок обновления:

1. перенести данные — `pg_upgrade` или `pg_dumpall` с восстановлением;
2. `postgresql_remove_other_versions: true` — **удаляет старый кластер вместе с базами**;
3. прогнать роль, после чего вернуть флаг в `false`.

Флаг существует именно потому, что удаление данных не должно быть побочным эффектом смены
номера версии.

Отдельная тонкость: `postgresql-common` создаёт кластер в postinst только если порт свободен.
Установка рядом с работающим старым кластером оставляет новую версию **вообще без кластера**,
и удаление старого его задним числом не создаёт — поэтому роль создаёт кластер явно, а не
полагается на пакет.

## Статистика запросов PostgreSQL

Медленный лог (`log_min_duration_statement = 500`) ловит запрос, который тормозит **однажды**.
Но запрос на 20 мс, вызываемый 100 000 раз в сутки, в него не попадёт никогда — а по суммарному
времени он может быть первым в базе, и индекс просит именно он. Это видно только через
`pg_stat_statements`, который агрегирует по нормализованному тексту запроса.

Включено по умолчанию (`postgresql_stat_statements: true`). Расширение ставится в служебную базу
`postgres`: представление показывает статистику **всего кластера** независимо от того, из какой
базы смотреть, поэтому роль по-прежнему не знает про базы конкретных сайтов.

Топ по суммарному времени:

```sql
SELECT calls,
       round(total_exec_time::numeric)     AS total_ms,
       round(mean_exec_time::numeric, 2)   AS mean_ms,
       rows,
       left(query, 120)                    AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

С сервера — одной командой:

```bash
sudo -u postgres psql -d postgres -c "SELECT calls, round(total_exec_time::numeric) AS total_ms, \
round(mean_exec_time::numeric, 2) AS mean_ms, rows, left(query, 120) AS query \
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;"
```

Два подвоха, оба стоили бы минуты на сервере:

- колонки называются `total_exec_time`/`mean_exec_time`, а не `total_time`, как в старых рецептах
  из интернета: их переименовали в PG 13, а роль ставит 18 (`postgresql_version`);
- `::numeric` обязателен: времена хранятся как `double precision`, а двухаргументного
  `round(double precision, integer)` в PostgreSQL нет — без приведения запрос падает.

`pg_stat_statements.save` по умолчанию `on`, поэтому статистика переживает рестарт и копится
с момента последнего сброса. После добавления индекса старые цифры продолжат тянуть картину
назад — сбросить, чтобы получить чистую базу для замера:

```sql
SELECT pg_stat_statements_reset();
```

**`shared_preload_libraries` — списочный параметр, и PostgreSQL берёт последнее присваивание
целиком**, синтаксиса «дописать» у него нет. Поэтому роль пишет весь список разом, а не
отдельной строкой на библиотеку. Второй потребитель (`auto_explain`, `pg_cron`) добавляется
в `postgresql_shared_preload_libraries`, а не вторым конфигом — иначе он молча вытеснит
`pg_stat_statements`.

**Про рестарт.** Роль рестартит PostgreSQL при любом изменении своего `99-krot.conf`, а не только
этой строки: часть параметров в файле (`shared_preload_libraries`, `shared_buffers`,
`max_connections`, `logging_collector`) — postmaster-level, и `reload` принимает их молча, не
применяя. Разделять reload и restart по типу параметра роль не пытается: цена ошибки —
настройка, которая по конфигу применена, а по факту нет. Рестарт занимает пару секунд, но это
простой всех сайтов на машине, поэтому прогон без изменений конфига базу не трогает вовсе.

## Посещаемость

Роль `goaccess` строит отчёты по логам nginx — **без единого скрипта на сайтах**. Счётчик от
третьей стороны на сети доменов был бы прямой уликой связи между ними, а данные тут не покидают
машину.

Отчёт **на каждый сайт отдельно**, никогда общий: одна страница со всеми доменами и есть тот
самый список, ради которого сеть прячут.

Сайты роль находит сама по vhost'ам в `sites-enabled`; перечислять их в inventory значило бы
положить список сайтов в конфигурацию машины.

### Два отчёта на сайт: весь трафик и только люди

На сайт строятся **две страницы**:

| путь | что показывает |
|------|----------------|
| `<домен>.html` | весь трафик, включая ботов |
| `humans/<домен>.html` | то же самое, но с `--ignore-crawlers` |

Оба нужны, потому что отвечают на разные вопросы. Замер на berlindame.de: **94 уникальных
посетителя в полном отчёте против 37 в человеческом** — 57 из них краулеры. Полный отчёт не
говорит, сколько пришло людей; отчёт без ботов не показывает, ходит ли Googlebot вообще, а на
молодом сайте это важнее числа посетителей.

`--ignore-crawlers` фильтрует **строки лога**, а не выбирает разделы: панели (рефереры,
география, страницы) одни и те же в обоих, просто посчитаны по разному кругу посетителей.

Подкаталог, а не суффикс `<домен>-humans.html`, — чтобы всё, что перечисляет отчёты глобом
`*.html`, по-прежнему видело ровно один файл на домен и не разбирало имена. Выключается
`goaccess_humans_report: false`; тогда роль удаляет каталог, иначе страницы в нём остались бы
висеть, замерев на дне выключения, рядом с полным отчётом, который продолжает обновляться.

`--unknowns-as-crawlers` намеренно не используется: на замере он сдвинул счёт на один визит
из 37, что не стоит флага, значение которого читателю придётся выяснять.

**Половина сканеров ботами себя не называет.** `--ignore-crawlers` ловит только тех, у кого в
User-Agent есть `bot`, `crawler` или `spider`, а `GoogleOther`, `Dataprovider`,
`InternetMeasurement` и HTTP-библиотеки (`curl`, `Go-http-client`, `okhttp`) проходят как
посетители. Поэтому человеческий отчёт получает свой список — `goaccess_extra_crawlers`,
файл `/etc/goaccess/krot-crawlers.list`, подключаемый флагом `-b`.

Замер 2026-08-02: berlindame.de **41 → 36**, stadtdame.de **26 → 20**; `GoogleOther`,
`Dataprovider` и `UptimeRobot` исчезли из отчёта, а в списке браузеров остались только Chrome,
Safari, Firefox и Edge. В полном отчёте все они по-прежнему видны — он на то и полный.

Две грабли, обе стоили проверки:

- **Тип пишется `Crawlers`**, с заглавной и во множественном числе, как в штатном
  `/etc/goaccess/browsers.list`. Любое другое написание GoAccess принимает за новую категорию
  браузеров, и счётчик посетителей не падает, а **растёт** — измерено, 41 превращалось в 78.
- **`-b` дополняет штатный список, а не заменяет его**, поэтому склеивать файлы не нужно:
  боты, которых GoAccess знает сам, остаются отфильтрованными.

### Второе условие: поведение

Имени мало — часть сканеров ходит под видом обычного Chrome. Поэтому человеческий отчёт
требует **обоих условий сразу**: пройти список имён **и** вести себя как браузер.

Признак поведения — внутренний referer. Браузер, отрисовав страницу, грузит её картинки и
подставляет адрес страницы в `Referer`; сканер идёт по списку URL и referer не ставит.
Считается это двумя проходами `awk` до вызова GoAccess: сам он читает строки по одной и не
помнит, что тот же адрес делал раньше.

**Порог — два таких запроса, а не один** (`goaccess_humans_min_referers`). Замерено: сканер,
искавший `/.git/HEAD`, сделал 53 запроса, из которых **ровно один** нёс referer — проверки
«есть хотя бы один» ему хватило бы. Браузер же выдаёт их десятками. На berlindame.de порог 2
оставляет 6 адресов из 103, порог 3 — 5, то есть ответ не балансирует на границе.

Ни один признак поодиночке не работает, и это проверено с обеих сторон: **UptimeRobot сам себе
ставит** `Referer: https://berlindame.de` на `HEAD /` — его ловит только имя; а сканер под
видом Chrome невидим для списка имён — его ловит только поведение.

**Цена названа прямо:** одиночный `GET /` без картинок отбрасывается вместе со сканерами —
35 таких адресов, почти все из датацентров, но среди них мог быть человек, закрывший вкладку
сразу. Размен сознательно в сторону занижения: отчёт, завышающий посещаемость, выдумывает
аудиторию, которой нет.

**Разбор зависит от формата строки.** Адрес — третье поле только в текущем формате, где
впереди стоит `[$time_local]`. Строки, записанные до его добавления, начинаются с адреса, и
третьим полем там идёт имя хоста — счёт вёлся бы по «berlindame.de» как по посетителю. Такие
строки отсекает `grep '^\['` ещё при чтении логов, но `awk` проверяет это сам: зависимость
в одно удаление от того, чтобы молча считать имена хостов.

Идеальной цифры этот способ не даёт: часть сканеров ходит под видом обычного Chrome, и по
User-Agent их не отличить. `UptimeRobot` в списке потому, что это собственный монитор — 462
запроса из 1240 на berlindame, больше всех прочих вместе, и ни один из них не читатель.

### Версия GoAccess

Ubuntu 24.04 даёт 1.8.1, официальный репозиторий проекта — **1.11**. Роль подключает его по
умолчанию (`goaccess_upstream_repository`), ключ подписи вшит в роль (отпечаток
`C03B48887D5E56B046715D3297BD1A0133449C3D`, Gerardo Orellana — автор GoAccess), а не качается
в рантайме: провижининг не должен зависеть от доступности keyserver.

Ради чего: города в геолокации (появились в 1.10) и, по заявлению changelog, разбор быстрее на
35% при памяти меньше на 20%. **Ускорение я не проверял** — цифры для сравнения с 1.8.1 не
сохранились. Замер на 1.11: сборка трёх сайтов на 2673 строках — 1.3 с, пик памяти одного
отчёта — 12 МБ.

Пока репозиторий включён, пакет ставится с `state: latest`: иначе на машине с уже
установленной 1.8.1 добавленный репозиторий ничего бы не изменил — `present` означает «пакет
есть», и роль отчиталась бы успехом, не сделав ничего. Без репозитория остаётся `present`,
чтобы роль не обновляла молча пакет дистрибутива.

**Выключение репозитория не возвращает старую версию.** Apt не понижает сам, а роль этого не
делает намеренно: молча заменить рабочий бинарь на более старый — не то, о чём просили.
Понижение — вручную, `apt install goaccess=<версия>`.

### География

Страну даёт база MaxMind, которую ставит роль `geoip`, а не заголовок `CF-IPCountry`: у
GoAccess нет поля, куда принять готовый код страны, и подсунуть его можно было бы только заняв
колонку с другим смыслом. Поэтому `cf=` в формате логов по-прежнему пропускается через `%^`.

Включается одной переменной — `goaccess_geoip_database: /var/lib/GeoIP/GeoLite2-Country.mmdb`.
Пустая означает отчёт без панели: роль базу не ставит, потому что база нужна не только отчётам.

**Роль отказывается настраивать базу, которой нет на диске.** GoAccess не запускается, если файл
назван и отсутствует, — упали бы разом все отчёты на машине, а уже построенные остались бы
лежать, выглядя свежими.

Верна эта география только потому, что генератор vhost'ов проекта настраивает real-IP по
заголовкам Cloudflare: без него в логе был бы адрес CDN, и панель показывала бы его
датацентры — правдоподобно и неверно. Проверено сверкой с `cf=`: Швейцария 68, США 114,
Польша 30, Финляндия 26, Китай 27 — порядок совпадает с тем, что пишет Cloudflare.

Издание базы — `GeoLite2-City`: оно несёт оба уровня, и на 1.11 отчёт показывает города. На
логах busel это Лондон, Амстердам, Варшава, Минск, Берлин, Франкфурт, Гамбург. Цена — **64 МБ
против 8.4** у Country-версии.

Роль **удаляет базы, которых нет в `geoip_editions`**: переставшая обновляться копия ровно того
файла, на который кто-то может смотреть, хуже отсутствующей — она отвечает, но неверно, и по
ней не видно, насколько устарела. Если `goaccess_geoip_database` указывает на удалённое
издание, роль `goaccess` останавливает прогон и называет путь.

`geoip` требует **Account ID** и **License key** от MaxMind. Ключ показывают один раз при
создании и хранят хешем — потерянный не восстановить, только выпустить новый. Роль их не ищет:
переменные приходят из inventory проекта, как `nginx_auth_password`.

**Роль отчёты только строит и на этом останавливается.** Готовые файлы лежат в
`{{ goaccess_report_dir }}` (`/var/www/goaccess`, права `0750`, файлы `0640`), группа —
`goaccess_reader_group`. Открывает их проект: busel отдаёт их роутом `/traffic` под логином
своей админки. Отдавать их самой ролью значило бы знать, какая машина держит админку, на каком
домене она отвечает и как устроены её сессии, — ничего из этого не верно для следующей машины,
на которой роль запустят. Прежние версии роли поднимали для этого vhost на `127.0.0.1:8443` за
basic auth; роль его теперь удаляет, чтобы второй вход не остался жить на уже развёрнутых
машинах.

Ничего не считается в момент открытия страницы: сборку раз в час делает системный таймер
`krot-goaccess.timer`, читатель получает готовый файл. Живой режим GoAccess
(`--real-time-html`) не используется — он держал бы демон и порт ради страницы, которую
смотрят раз в день. Плата за это — **отчёт отстаёт до ~65 минут** (час плюс
`RandomizedDelaySec=300`). Сборка двух сайтов на 1919 строках логов укладывается в секунду;
цифра записана как точка отсчёта, потому что проход идёт по всем логам и растёт вместе с их
числом.

**Формат логов должен содержать время.** GoAccess без него не запускается вовсе
(`No time format was found`), поэтому `log_format` проекта обязан начинаться с `[$time_local]`.
Строки, записанные раньше, отбрасываются на входе: GoAccess не умеет терпеть ошибки разбора и
при полностью нечитаемом файле бросает его целиком, а не пропускает строки.

Отчёт **пересобирается с нуля** из всех логов, что лежат на диске, включая ротированные `.gz`.
Родной `--persist` тут не годится: он складывает поданное к накопленному и **не помнит, какие
строки уже видел**, поэтому лог, который ещё не ротировался, считается заново на каждом прогоне —
измерено, три запроса превращались в 3, 5, 7, 9 за четыре сборки. Пересборка означает, что цифры
зависят только от того, что на диске, а глубина истории равна сроку хранения в logrotate.

## Секреты

Роли берут пароли из Bitwarden в рантайме, в репозитории секретов нет. Перед прогоном хранилище
должно быть разблокировано, **и токен надо отдать плейбуку через окружение**:

```bash
BW_SESSION="$(cat /tmp/bw-$USER/session)" ansible-playbook site.yml
```

Lookup-плагин запускает `bw` сам и про кеш сессии не знает. Без переменной он видит хранилище
запертым и валит прогон — даже когда `bw status --session` из того же кеша отвечает `unlocked`.
Сообщение при этом жалуется на замок, а не на отсутствующую переменную.

Роль, которой нужен пароль, падает на `assert`, а не ставит пустой: пустой `htpasswd` пустил бы
на закрытый сайт кого угодно.

## Разработка

Архитектура и принятые решения — `openspec/ARCHITECTURE.md`. Изменения ведутся как в busel и
matilda: `openspec/changes/<дата>-<слаг>/` с `proposal.md` (зачем и что меняется) и `tasks.md`,
отработанные уезжают в `changes/archive/`.

```bash
yamllint .        # форматирование YAML
ansible-lint      # профиль production — строжайший
```

CI (`.github/workflows/lint.yml`) гоняет оба на каждый PR.

Все роли идемпотентны: повторный прогон даёт `changed=0`. Это не декларация — проверено
прогоном на живой машине.

Целевая платформа — Ubuntu 24.04 (noble).
