# Коллекция и её границы

Krot — это **коллекция ролей, а не плейбук машины**. В репозитории нет inventory и нет `site.yml`
для конкретных машин: они живут в busel и matilda, каждый со своими хостами и переменными.
Единственный плейбук коллекции — `site_launch`, порядок запуска сайта
([Запустить сайт](../runbooks/launch-a-site.md)): проект подставляет в него свои шаги, но не
меняет их порядок.

## Как проект подключает krot

```yaml
# requirements.yml проекта
collections:
  - name: git+https://github.com/haspadar/krot.git
    type: git
    version: main   # или тег, чтобы заморозить инфраструктуру
```

```bash
ansible-galaxy collection install -r requirements.yml
```

Зависимости (`ansible.posix`, `community.general`, `community.postgresql`) подтягиваются сами.

Это «composer-way»: `ansible-galaxy collection install` раскладывает коллекцию локально, как
`composer install` в `vendor/`. Не submodule и не symlink — обновление роли это смена `version`.

**Почему коллекция, а не набор ролей.** `ansible-galaxy` умеет ставить git-источник как **одну
роль**, а не как каталог ролей. Коллекция — единственная форма, в которой набор ролей ставится
одной командой и версионируется целиком.

Использование:

```yaml
- name: Provision the machine
  hosts: web
  roles:
    - role: haspadar.krot.common
    - role: haspadar.krot.php
    - role: haspadar.krot.nginx
    - role: haspadar.krot.firewall
    - role: haspadar.krot.fail2ban
```

Голая машина — сперва один раз под root:

```yaml
- name: Bootstrap SSH access
  hosts: new
  roles:
    - role: haspadar.krot.bootstrap
      vars:
        bootstrap_authorized_keys: ["ssh-ed25519 AAAA..."]
```

```bash
ansible-playbook bootstrap.yml -u root -k
```

## Главный принцип: два набора ролей, и ни один не знает проект

Это не стилистика, а то, что удерживает роли переносимыми. **Как только роль узнаёт имя проекта,
его конфиг или команды, она перестаёт быть общей и превращается в конфиг одной машины.**

- **Роли машины** (`common`, `nginx`, `postgresql` …) не знают про сайты вовсе.
- **Роли сайта** (`site_*`) знают **один** сайт — тот, что передан переменными `site_*`: домен,
  зону, базу. Но не знают, **чей** он: наполнение, деплой, открытие и запись полученных ID
  подключаются task-файлами проекта.

До 2026-09-26 принцип звучал «роль знает про хост, но не про приложения на нём», и провижининг
сайта был отдан проектам. Запуск жил в двух местах — командах busel и шагах gudok, — и грабли,
найденные в одном, переоткрывались в другом. Решение владельца: инструмент один, роли в krot;
пересмотр подтверждён тогда же (change `2026-09-26-site-launch`).

| Слой | Что делает | Инструмент |
|------|-----------|-----------|
| Провижининг **машины** | юзер, пакеты, firewall, fail2ban, (docker \| php+pg+nginx) | **роли машины** krot |
| Запуск **сайта** | зона, NS у регистратора, записи, Origin CA, БД сайта, счётчики, поисковики | **роли сайта** krot, плейбук `site_launch` |
| Проектные шаги сайта | наполнение, vhost, деплой, открытие, запись ID | task-файлы проекта |
| Выкатка **кода** | релизы, symlink, reload | **Deployer** (`deploy.php`) в каждом проекте |

Пересечение Ansible и Deployer ровно одно: Ansible создаёт операторского юзера (`bootstrap_user`,
по умолчанию `km`) и — если проект указал `nginx_deploy_root` — каталог под релизы с правами, куда
Deployer потом кладёт выкатки.

**Путь каталога роль не знает.** `nginx_deploy_root` по умолчанию пуст, и тогда задача пропускается
вовсе: `/var/www/<project>` — соглашение проектов, а не константа роли. Иначе роль знала бы имя
проекта, а это ровно то, чего принцип выше запрещает.

## Что роли намеренно НЕ делают

Каждый пункт — не забытое, а отданное другому владельцу.

| Не делает | Кто владелец | Почему не роль |
|---|---|---|
| vhost'ы конкретных сайтов | генератор проекта | роль владеет только `sites-available`/`sites-enabled` и правами |
| `log_format` | тот же генератор | он знает имя формата, которое называют его конфиги; имя — по сети |
| базы сайтов на уровне машины | роль сайта `site_database` | роль `postgresql` ставит только сервер |
| выкатку кода | Deployer проекта | роль `deploy` лишь запускает его; релизы и rollback в `deploy.php` |

Real-IP и сервер по умолчанию, наоборот, **роль делает** (по флагам), хотя они выглядят как
настройки сайтов: nginx принимает их один раз на машину, а сетей на машине бывает несколько.
**Два писателя на одну настройку неизбежно разъезжаются** — пока сеть одна, единственный писатель
её генератор; со второй сетью им может быть только то, что про сети не знает. Подробнее —
[Cloudflare-замок](../operations/cloudflare.md).

## Два набора ролей

| Проект | Роли | Почему так |
|---|---|---|
| busel | `common + php + postgresql + nginx + umami + firewall + fail2ban` | несколько сайтов на машине за Cloudflare, всё системное |
| matilda | `common + docker + firewall + fail2ban` | голый хост под Docker Compose |

Разница не в предпочтениях. У matilda тяжёлое специфичное окружение (playwright, flaresolverr,
minio, postgres, php, api), и его воспроизводимость **уже решена** compose'ом — машине остаётся
подготовить хост. У busel сайты простые и сервисы системные: Docker дал бы оверхед на слабых VPS
и вторую систему выкатки поверх Deployer.

Каждая роль атомарна и применима отдельно. Все параметры — в `roles/<role>/defaults/main.yml`.

## Облако — в ролях сайта, а не в Terraform

Раньше здесь стояло: «Terraform в krot нет и не будет; CF-зоны и DNS, домены Dynadot — ему,
смешивать с провижинингом машины значит потерять границу». Terraform так и не появился, а запуску
нужен **порядок шагов**, который декларативное состояние не выражает: зона → NS у регистратора →
ожидание делегирования → записи → сертификат до деплоя. Поэтому зоны, записи и регистратор
перешли в роли сайта (решение 2026-09-26).

Граница сохранилась, но проходит иначе: не «облако против сервера», а **роли машины против ролей
сайта**, в одной коллекции разными наборами. Облачные вызовы идут с control-машины
(`delegate_to: localhost`), токены на сервер сайта не уезжают. R2 и прочее облако вне запуска
сайта этим решением не затронуты.

## Целевая платформа

Ubuntu 24.04 (noble). Все роли идемпотентны: повторный прогон даёт `changed=0`. Это не декларация
— проверено прогоном на живой машине, и каждое изменение роли проверяется тем же способом.

```bash
yamllint .        # форматирование YAML
ansible-lint      # профиль production — строжайший
```

CI (`.github/workflows/lint.yml`) гоняет оба на каждый PR — плюс `ansible-galaxy collection build`,
`wiki-lint`, `secret-lint`, сверку `wiki/index/` с источниками и `coverage.py`. Сценарии molecule
идут отдельными job'ами, по одному на сценарий; обязательны для мержа `lint` и `molecule`, и второе
имя держит job-агрегатор — [operations/testing-roles.md](../operations/testing-roles.md).
