# Дневная статистика поиска

Роль collecting получает дневные метрики GSC отдельным заданием gsc. Сайты объявляет потребитель,
а сборщик не знает групп эксперимента, страниц админки или исходной линии появления страниц.
Настройки перечислены в `roles/collecting/defaults/main.yml`, точный DDL —
`roles/collecting/files/schema.sql`. Работа роли проверяется сценарием molecule collecting,
API — фейками. Эти проверки не подтверждают живой доступ Performance: его проверяет потребитель
при переносе после применения роли.

## Что читатель получает

В krot_collect находятся независимые search_query (query/country/device), search_page (page) и
search_page_query (page/query). Во всех: site, day, search_type, impressions, clicks, position,
collected_at. Дни — America/Los_Angeles, search_type — web, запросы явно используют final.
Строки запросов не восстанавливают итоги страниц: анонимизированные запросы и ограничения API
не позволяют считать сумму детализации итогом сайта.

search_day — успешный календарь по site/day/search_type/dataset. pagination_complete говорит,
что все доступные страницы API получены; coverage_limited=true означает, что Google всё равно
не гарантирует все строки. finalized означает, что день раньше первой незавершённой даты Google.

Её задание спрашивает в начале ночи у каждого сайта: запрос `dataState: all` по дате за
последние 30 дней отвечает `metadata.firstIncompleteDate`, и все дни раньше неё окончательны.
Поэтому день без показов — успешный отчёт с row_count=0, а не пропуск: Google просто не
называет даты без строк, и прежняя проверка по final-отчёту путала тишину с незавершённостью.
День начиная с этой даты получает attempt unavailable без запросов отчётов.

⚠️ Ответ без строк приходит без metadata. Такой сайт берёт самую раннюю дату, названную другими
сайтами той же ночи (замер 2026-10-03: у двух property одна и та же дата, а последняя final —
накануне). Если не назвал никто или запрос сайта отказал, решает прежняя проверка дня по
final-отчёту: дата без строк остаётся unavailable, без маркера — неизвестное не становится
нулём. Ноль, записанный по слишком ранней границе, перечитывается в окне overlap_days.

search_attempt хранит начало, завершение, status и безопасную причину отказа. Running после
оборванного процесса остаётся следом незавершённой попытки, а не успехом. Каждая пара отчёт/день
заменяется целиком вместе с маркером и успехом попытки в одной транзакции. Другой отчёт может
успеть независимо: анализ, требующий три набора, проверяет календарь всех трёх.

## Ночь и свежесть

Первый сбор спрашивает минимум 28 предыдущих дней. Затем пересобирает недавнее окно и чинит
пропуски начиная с самой ранней известной даты данных, маркеров или попыток либо начального
окна — что раньше. Отказавший первый день не исчезает после сдвига окна.
Старше срока хранения запросов нет. Отказы одного сайта не исключают остальные; отказ доступа,
базы или метрик красит задание. Данные старше freshness_days или отсутствие успешной истории
тоже красит задание. Нулевая история приписывается сайту только по границе Google, своей или
заимствованной; без неё тихие дни остаются unavailable, и свежесть честно краснеет.

Программа общая на машину: обходы читают версии схемы 1 и 2, пока другие проекты не
обновили свои базы; GSC требует version 2.

Два одновременных сборщика одной базы исключены advisory lock. При отказе API старые строки
остаются. История и попытки удаляются вместе по retention_months, только для объявленных сайтов.
Это хранение отличается от окна обходов nginx: его срок остаётся прежним.

## Перенос без остановки краулеров

Добавить gsc к jobs, оставив timers:true и disabled_timers:[gsc]. Роль подготовит схему, ключ и
выключенный GSC-таймер; ranges/crawl продолжают работу. timers:false выключает все задания
проекта. Ключ нужен даже при выключенном таймере: он хранится отдельно в
/etc/krot-collect/<проект>.google.json с правами 0600; публичный JSON и экспорт его не содержат.

После подготовки потребитель импортирует историю, сохраняя collected_at, старые известные
флаги и provenance=imported. Неизвестная полнота — NULL, не true. Последние дни старой истории,
помеченные только фактом запроса, нельзя автоматически объявлять final. Исходная линия появления
страниц остаётся у потребителя и не пересоздаётся. Повторный импорт не должен возвращать строки,
которые новый сбор уже удалил: проверяется весь день, а не только конфликт отдельных ключей.

Потребитель переключает читателей и выключает собственные GSC-проходы; сбор других движков и
предварительный часовой сбор остаются его задачей. После сверки убирается gsc из disabled_timers.
Сам сборщик ничего не переносит и не меняет baseline.

## Проверить и прочитать

```fish
systemctl list-timers 'krot-collect-*'
journalctl -u krot-collect-<проект>-gsc -n 50
sudo -u krot_collect env PYTHONPATH=/usr/local/lib/krot-collect python3 -m krot_collect --config /etc/krot-collect/<проект>.json gsc --from 2026-09-01 --to 2026-09-28
```

Для CLI нужен PYTHONPATH=/usr/local/lib/krot-collect, как у сервисного юнита. Явный диапазон
не включает сегодня в PT и не выходит за retention; свежесть при таком backfill не оценивается.

Приложение и extra_readers получают CONNECT/USAGE/SELECT и SELECT на будущие таблицы.
Записывающих прав роль им не даёт. Отдельный аналитик получает доступ только если его существующая
SQL-роль объявлена явно. Экспорт — команда CLI export с --from/--to: JSONL
{contract_version:1,dataset,row} по объявленным сайтам, данным, календарю и попыткам, в одной
read-only snapshot-транзакции. Экспорт не требует сервисного ключа и не создаёт публичного HTTP.
Наличие договора экспорта не означает, что доступ внешнего потребителя уже настроен.
