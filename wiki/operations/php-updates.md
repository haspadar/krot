# Обновление PHP

Начиная с 14.0.0 роль `php` по умолчанию разрешает обновления packages.sury.org через уже
включённый unattended-upgrades (обычно его устанавливает роль `common`). Патч приходит
без ручного apt и повторного Ansible. `php_packages_state: present` управляет только
прогоном Ansible: это не запрет фонового обновления.

Флаг `php_unattended_upgrades: true` создаёт `/etc/apt/apt.conf.d/53-krot-php-unattended`
со строкой `deb.sury.org:${distro_codename}`. Origin и codename сверены 22.11.2026:
`o=deb.sury.org,a=noble,n=noble` (Label отсутствует). Файл читается после `52-krot-unattended`, где
`common` очищает унаследованный список и задаёт три источника безопасности Ubuntu.
Поэтому повторный прогон `common` не стирает разрешение PHP. При `false` роль удаляет
только свой файл; источники Ubuntu остаются. Другие пользовательские apt-конфиги
по-прежнему могут добавлять или переопределять настройки.

У Sury нет отдельного security pocket: разрешаются все допустимые обновления этого origin,
включая сопутствующие пакеты, а не только исправления CVE выбранной ветки. Роль устанавливает
версионные пакеты и сама не меняет `php_version`. Неверсионные метапакеты (`php`, `php-fpm`),
добавленные проектом отдельно, могут подтянуть другую ветку при смене своих зависимостей.
Пакет может перезапустить FPM; краткий обрыв запросов
принимается ради своевременных патчей. Автоматическую перезагрузку машины `common`
оставляет выключенной. `php` не устанавливает и не включает unattended-upgrades вместо
`common`; на машине без работающего автомата одно разрешение ничего не запускает.

## Проверка автомата и отставания

`apt-config dump` должен показывать три Ubuntu-origin и Sury, а
`apt-cache policy php8.5-common` — origin кандидата `deb.sury.org` с codename машины.
На тестовой машине `unattended-upgrade --dry-run -d` показывает допустимые источники
и решение об обновлении; он может писать служебные логи, поэтому для проверки боевой
машины только чтением достаточно конфигурации и policy. Наличие кандидата не доказывает
успешную установку: держатели пакетов, зависимости и ошибки автомата проверяются отдельно.

Роль `updates_monitor` читает фактическую политику unattended-upgrades и видит новый
origin без отдельного списка. Для доставки тревог потребитель должен включить роль,
настроить приватный HTTPS-путь и контакт UptimeRobot: [порядок](update-monitoring.md).

## Миграция с замороженного PPA

Автор прекратил обновления ondrej/php и перенёс Ubuntu-пакеты в packages.sury.org.
[Инструкция автора](https://packages.sury.org/php/README.txt) указывает новый репозиторий
и keyring. Ключ вендорен: `15058500A0235D97F5D10063B188E2B695BD4743`,
сверен с [публикацией автора](https://www.patreon.com/posts/dpa-new-signing-25451165)
и подписью noble InRelease 22.11.2026; срок ключа — до 04.02.2028.

Потребитель обновляет коллекцию до 14.0.0, оставляет `php_version` и свой список расширений,
проверяет работающий unattended-upgrades из `common` и применяет роль `php`.
`php_unattended_upgrades` сохраняет прежний смысл, `php_packages_state: present` не
обновляет уже установленный PHP немедленно. Для миграции с немедленным патчем применить
`php_packages_state: latest`; иначе обновление выполнит автомат по своему расписанию.
Перед этим сохранить полный комплект установленных пакетов для отката.

Ожидаемые изменения: `/etc/apt/sources.list.d/debsuryorg-php.sources`, встроенный в него ключ (Signed-By), новый origin в `53-krot-php-unattended`;
удаляются `ondrej-ubuntu-php.sources`, `ondrej-ubuntu-php-noble.sources` и
`/etc/apt/keyrings/ondrej-ubuntu-php.asc`. Роль обновляет APT после удаления старых
источников, поэтому смена Label замороженного PPA не мешает миграции.
Иные вручную добавленные записи PPA и ключи вне этих путей оператор проверяет отдельно.

APT выбирает наиболее новую Debian-версию, без `allow_downgrade`; транзакция с удалением
пакетов останавливается через `fail_on_autoremove`. Установленная ветка сохраняется.
Molecule начинает с настоящего PHP из PPA, проверяет сохранность каждого установленного
пакета и версию не ниже исходной, кандидата Sury и соответствие политике автомата и мониторинга.

Для возврата источника остановить автоматическое обновление PHP флагом
`php_unattended_upgrades: false`, сохранить конфиги источников, убрать новый `.sources`
со встроенным ключом, затем восстановить источник старой роли из последнего релиза до 14.0.0
(достаточно одной записи PPA, дубликат не восстанавливать). Обновление индекса PPA может
потребовать принятия смены Label через `apt-get update --allow-releaseinfo-change-label`.
Возврат источника сам по себе не понижает установленный PHP и не возвращает патчи:
PPA заморожен. Для отката бинарников нужен полный сохранённый комплект `.deb` и явное
`--allow-downgrades` одной транзакцией, как описано ниже. Повторное применение старой
коллекции без удаления Sury не является откатом источника.

## Срочный патч

В плейбуке проекта, где роль подключена (у krot своего плейбука нет; тег — тот, под которым
проект подключил роль, если подключил):

```bash
ansible-playbook site.yml --tags php -e php_packages_state=latest
```

С `latest` роль поднимает **все установленные пакеты ветки**: `php<версия>`, `php<версия>-*`,
`libapache2-mod-php<версия>` и `libphp<версия>-*`, а не только перечисленные в `php_extensions`. Иначе на машине, где проект доставил своё расширение, ничего бы
не держалось: каждое расширение зависит от `php<версия>-common` строго той же версии, и apt
выбирал бы между обновлением пакета и его удалением. Ветку `php_version` прогон не меняет:
переход между минорными версиями — отдельная работа.

## До прогона: откат

**Прежней версии в индексе PPA может уже не быть.** В день патча 22.10.2026 `apt-cache madison`
показывал одну строку, новую версию, и откатиться «через apt» было нечем. Прежние пакеты
остаются в `/var/cache/apt/archives/`, если кеш не чистили. Их стоит скопировать в отдельный
каталог до прогона: `apt-get autoclean` удаляет пакеты, которых больше нет в индексе.

Сохранять надо всё, что роль обновит, то есть те же пакеты ветки, включая
`libapache2-mod-php<ветка>` и `libphp<ветка>-*`, если они стоят. Каждый из них привязан к
`php<ветка>-common` строгой версией, поэтому откат одного `common` без них apt не разрешит или
разрешит удалением SAPI.

```bash
d=/root/php-rollback-<старая версия>
sudo mkdir -p $d
sudo cp /var/cache/apt/archives/{php,libphp,libapache2-mod-php}<ветка>*_<старая версия>_*.deb $d/
# комплект полон, если числа совпадают; без отбора по ii dpkg-query считает и
# пакеты, которых на машине нет, но о которых dpkg помнит
dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' | awk '$1 == "ii" {print $2}' \
  | grep -cE '^(lib|libapache2-mod-)?php<ветка>(-|$)'
ls $d | wc -l
# откат одной транзакцией: sudo apt-get install --allow-downgrades $d/*.deb
```

Если в кеше пусто, пакеты ещё какое-то время лежат в пуле PPA по прямому адресу
(`https://ppa.launchpadcontent.net/ondrej/php/ubuntu/pool/main/p/php<ветка>/`). Launchpad удаляет
вытесненные версии не сразу, но и не держит их вечно.

Перед прогоном стоит снять коды ответа сайтов и список `systemctl --failed`: после прогона
сравнивать надо с этим, а не с ожиданием.

## После: чем доказывается, что патч дошёл

Нулевой код возврата и `changed` у задачи доказывают только, что пакеты распаковались. Что
работает новый код, доказывают:

| Проверка | Почему именно она |
|---|---|
| `php -v` и `php-fpm<ветка> -v` | CLI и FPM — разные бинари из разных пакетов |
| `readlink /proc/<pid>/exe` у мастера и воркеров FPM | процесс, не перезапущенный после обновления, указывает на `(deleted)` и продолжает исполнять старый код |
| `php-fpm<ветка> --test`, `nginx -t` | конфиги пакета могли разойтись с конфигами роли |
| коды ответа сайтов против снятых до прогона | 502 на всех сайтах при `active` у FPM — обычная картина сломанного сокета |
| `systemctl --failed` против снятого до прогона | упавшие задолго до прогона юниты не должны записываться на его счёт |

Пакет перезапускает FPM сам, двумя циклами stop/start подряд. Запросы, пришедшие в эти секунды,
обрываются (в nginx `connect() ... failed` и `Connection reset by peer`); это ожидаемо и
проверяется тем, что после перезапуска таких строк нет.

## Чего роль не касается

PHP внутри Docker-образов роль не видит и не обновляет: образ пересобирает проект, которому он
принадлежит. При патче их нужно перечислить отдельно.

Замер первого такого обновления — [патч PHP 22.10.2026](../research/2026-10-22-php-security-patch.md).

Проверка задержавшихся обновлений и сервисов после патча — [мониторинг обновлений](update-monitoring.md)
