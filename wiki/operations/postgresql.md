# PostgreSQL

Роль ставит **только сервер**: базу сайта создаёт роль сайта `site_database`, владельцем —
роль PostgreSQL самого сайта, которую заводит проект (без неё `site_database` останавливается, а
не создаёт базу от postgres). Иначе плейбук машины начал бы знать про конкретные сайты, а он
должен быть про хост ([Запустить сайт](../runbooks/launch-a-site.md)).

Версия — `postgresql_version`, сейчас **18**, ставится из pgdg. Логи — csvlog со slow-query логом,
ротирует себя сам.

## Мажорная версия не поднимается сменой переменной

`postgresql_version` — это версия, которую роль **ставит**, а не обновление уже работающей.
PostgreSQL не читает каталог данных предыдущей мажорной версии: поднятие переменной с 16 на 18
ставит **второй кластер рядом**, а не апгрейдит первый.

Дальше происходит незаметное: `pg_createcluster` берёт первый порт, не занятый существующим
кластером, то есть 5433, а конфиг роли объявляет 5432 — новый кластер не стартует, приложение
продолжает работать со старым, **и всё выглядит исправным**.

Поэтому роль **отказывается** прогоняться рядом с кластером чужой версии и называет причину.

Порядок обновления:

1. перенести данные — `pg_upgrade` или `pg_dumpall` с восстановлением;
2. `postgresql_remove_other_versions: true` — **удаляет старый кластер вместе с базами**;
3. прогнать роль, после чего вернуть флаг в `false`.

Флаг существует именно потому, что удаление данных не должно быть побочным эффектом смены номера
версии.

Две тонкости:

- **Кластеры определяются по `pg_lsclusters`, а не по каталогам `/etc/postgresql`.** Пакет, чей
  postinst не смог создать кластер (порт занят), всё равно оставляет за собой конфиг-каталог —
  проверка по каталогам увидела бы кластер, которого нет.
- **`postgresql-common` создаёт кластер в postinst только если порт свободен.** Установка рядом с
  работающим старым кластером оставляет новую версию **вообще без кластера**, и удаление старого
  его задним числом не создаёт. Поэтому роль создаёт кластер явно, а не полагается на пакет.

## Статистика запросов

Медленный лог (`log_min_duration_statement = 500`) ловит запрос, который тормозит **однажды**. Но
запрос на 20 мс, вызываемый 100 000 раз в сутки, в него не попадёт никогда — а по суммарному
времени он может быть первым в базе, и индекс просит именно он. Это видно только через
`pg_stat_statements`, который агрегирует по нормализованному тексту запроса.

Включено по умолчанию (`postgresql_stat_statements: true`). Расширение ставится в служебную базу
`postgres`: представление показывает статистику **всего кластера** независимо от того, из какой
базы смотреть, поэтому роль по-прежнему не знает про базы конкретных сайтов.

Топ по суммарному времени:

```sql
SELECT calls,
       round(total_exec_time::numeric)     AS total_ms,
       round(mean_exec_time::numeric, 2)   AS mean_ms,
       rows,
       left(query, 120)                    AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

С сервера — одной командой:

```bash
sudo -u postgres psql -d postgres -c "SELECT calls, round(total_exec_time::numeric) AS total_ms, \
round(mean_exec_time::numeric, 2) AS mean_ms, rows, left(query, 120) AS query \
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;"
```

Два подвоха, оба стоили бы минуты на сервере:

- колонки называются `total_exec_time`/`mean_exec_time`, а не `total_time`, как в старых рецептах
  из интернета: их переименовали в PG 13;
- `::numeric` обязателен: времена хранятся как `double precision`, а двухаргументного
  `round(double precision, integer)` в PostgreSQL нет — без приведения запрос падает.

`pg_stat_statements.save` по умолчанию `on`, поэтому статистика переживает рестарт и копится с
момента последнего сброса. После добавления индекса старые цифры продолжат тянуть картину назад —
сбросить, чтобы получить чистую базу для замера:

```sql
SELECT pg_stat_statements_reset();
```

## `shared_preload_libraries` — список, за который дерутся

PostgreSQL берёт **последнее присваивание целиком** и не умеет дописывать. Поэтому роль пишет весь
список разом из переменной, а не отдельной строкой на библиотеку.

Второй потребитель (`auto_explain`, `pg_cron`) добавляется в
`postgresql_shared_preload_libraries`, а не вторым конфигом — иначе он молча вытеснит
`pg_stat_statements`.

Если преднагружать нечего, строка не пишется вовсе: параметр остаётся `default`, а не фиксируется
как `''`, который затёр бы чужое значение.

## Про рестарт

Часть параметров в `99-krot.conf` (`shared_preload_libraries`, `shared_buffers`,
`max_connections`, `logging_collector`) — postmaster-level, и `reload` **принимает их молча, не
применяя**. Рестарт же — простой всех сайтов машины: на машине без пула соединений это 5xx на
каждом сайте.

Поэтому решает сервер (`roles/postgresql/files/apply-settings.sh`), в три шага:

1. `postgres -C` читает все файлы так, как прочтёт их стартующий сервер. Невалидное значение
   где угодно — отказ прогона, сервер не тронут даже reload'ом: reload такого файла всё равно
   применил бы его валидные строки. Это проверка, а не сравнение.
2. Файл новее последней загрузки конфига (`pg_conf_load_time()`) — reload.
3. `pg_settings.pending_restart` — список изменённых postmaster-параметров, которые сервер
   принял, но применит только рестартом, включая выброшенный из файла (выключенный
   `pg_stat_statements`). Есть такие — рестарт, нет — всё.

`postgres -C` не проверяет параметры расширения: библиотека в нём не загружена, и они остаются
сырым текстом. Значения `pg_stat_statements` роль поэтому проверяет сама, первой задачей (`max`
от 100, `track` из none/top/all), — иначе сервер отверг бы их при reload, оставив старые, а
прогон отчитался бы успехом.

⚠️ **`ALTER SYSTEM` сильнее роли.** `postgresql.auto.conf` читается после `conf.d`, и значение,
поставленное там руками, перекрывает файл роли. Замер 2026-10-03 на рабочей машине: первый прогон
8.0.0 выключил запись подключений, отчитался успехом, а подключения писались дальше — их держал
месячной давности ручной `ALTER SYSTEM`. С 8.2.0 роль ищет в `pg_file_settings` более позднее
присваивание того же имени в другом файле — по `seqno`, а не по `applied`: победитель может сам
ждать рестарта, и тогда `applied` ложно у обеих строк. Найдено — прогон падает, называя файл и
строку, которые победили, но **после** рестарта: упавший рестарт должен успеть откатиться.

Файл роли при этом не откатывается — он верный; снимать надо перекрытие:
`ALTER SYSTEM RESET <имя>`. Перечитывать руками не нужно: роль сравнивает время загрузки конфига
со всеми его источниками, включая `postgresql.auto.conf`, и следующий прогон перечитает сам.
Перекрытие тем же значением тоже отказ: правило «действует то, что написала роль» проще, чем
«действует то же, что написала роль». Перекрытые ролью строки пакетного `postgresql.conf` —
норма, так задумано.

Откатывают файл только две причины: отказ проверки — код 64, а не 2: код 2 у psql и sed значит
«нет соединения» или «нет файла», и правильный файл откатился бы из-за недоступного сервера
(прежний файл на место, сервер не тронут); и старт или рестарт, который не поднял сервер
(прежний файл на место, сервер запускается на нём). Старт лежащего сервера идёт внутри того же
блока, поэтому и он откатывается. Файл,
созданный этим же прогоном, при этом удаляется, а не изменённый прогоном — остаётся: вернуть
его не к чему. Остальные отказы (psql недоступен, reload не дошёл) роняют прогон без отката —
новый файл может быть верным, и откатывать его по чужой причине значит потерять правку.

Решение принимается по состоянию сервера, а не по тому, менял ли прогон файл, поэтому прерванный
прогон доделывает следующий. Порт берётся из `postmaster.pid` работающего сервера, а не из нового
файла: сменённый порт — это и есть параметр, ждущий рестарта.

⚠️ Два способа, которые выглядят проще и не работают, — оба прошли через ревью до выпуска:

- **сообщения `pg_file_settings`**: `setting could not be applied` PostgreSQL 18 пишет и для
  параметра, требующего рестарта, и для невалидного значения — разбор их при `work_mem: 0`
  перезапустил бы базу в конфиг, который она отвергнет;
- **сравнение значений** `postgres -C` с `pg_settings.setting`: одно значение печатается
  по-разному (права файла восьмерично и десятично, параметр расширения сырым текстом, пока
  библиотека не загружена), и каждое такое различие становилось reload или рестартом на каждом
  прогоне.

⚠️ Чего проверка не ловит: значение, допустимое для параметра, но роняющее сам старт
(`max_connections` меньше зарезервированных соединений, несуществующая preload-библиотека,
`shared_buffers` больше памяти машины без overcommit) — `postgres -C` выходит раньше этих проверок. Рестарт тогда
падает, и роль возвращает прежний файл и запускает сервер на нём: сайты лежат секунды, а не до
ручного вмешательства. Прежняя схема, рестартовавшая на любую правку, оставляла базу лежать.

До 8.0.0 роль рестартила при любом изменении файла: классификация по типу параметра казалась
риском «применено по конфигу, но не по факту». Риск был в ручном списке; `pending_restart` его не
несёт. Сценарий molecule проверяет шесть путей — `pg_stat_statements.max: 0` отвергнут до любой
работы — и ещё пять: `max_connections` поверх запущенного сервера —
рестарт; `work_mem` — reload без сдвига времени старта postmaster; `work_mem: 0` — отказ без
касания сервера и прежний файл на диске; несуществующая preload-библиотека — упавший рестарт, прежний файл и
поднятый на нём сервер; выключенный `pg_stat_statements` — рестарт.
