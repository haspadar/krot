# Паспорт сайта

Роль `site_passport` кладёт на машину статичный JSON, в котором сайт сообщает общему учёту сети
свою страну, профиль, дату запуска и происхождение домена:

```
GET https://<домен>/<путь>
200 application/json
{"country":"KZ","profile":"str-esc","launched":null,"origin":null}
```

Замок — сам путь: `"/" + sha256("<секрет>:<домен>")[:16]` (hex). Домен берётся в нижнем регистре,
без `www` и без точки на конце. Токена и заголовков авторизации нет: кто не знает секрета, не
найдёт файла. Читающая сторона считает путь той же формулой.

## Что роль делает и чего не делает

| Делает | Не делает |
|---|---|
| кладёт `/var/lib/krot-passport/<домен>/<путь>` (каталоги `0711`, файл `0644`) | не правит вхосты |
| пишет фрагмент `/etc/nginx/snippets/krot-passport-<домен>.conf` (`0640`) с точным `location` | не включает фрагмент: `include` ставит тот, кто пишет вхосты |
| останавливает выкатку `assert`'ом без страны, профиля, короткого секрета, при домене не вида DNS-имени с точкой (`../etc`, `localhost`), при кривой дате и неверном `origin` | не создаёт и не читает секрет |
| убирает паспорт прежнего секрета в каталоге домена после перезагрузки `nginx`, если фрагмент в этом прогоне изменился (оговорка — в «Что кусается») | не входит в `site_launch` |

Роль знает один сайт и не знает, чей он; вхосты и выкатка кода — дело проекта
([границы коллекции](../domains/collection-layout.md)).

## Переменные

Лежат в `roles/site/defaults/main.yml` (раздел Passport), как у остальных `site_*`:

| Переменная | Смысл |
|---|---|
| `site_domain` | домен сайта (общая для всех `site_*`) |
| `site_passport_country` | ISO 3166-1 alpha-2 в верхнем регистре, обязательна |
| `site_passport_profile` | один из `site_passport_profiles`, обязательна |
| `site_passport_launched` | `YYYY-MM-DD` или `null` |
| `site_passport_origin` | строго строка `new` или `drop`, либо `null`; при отсутствии — `null` |
| `site_passport_secret` | значение секрета; короче `site_passport_secret_min_length` (24) — роль останавливается. `no_log` |

`origin` приходит только из инвентаря проекта-потребителя. Роль не выводит его из страны,
профиля или даты и не ведёт отдельный реестр. Другие значения и типы отклоняются до записи
любых файлов. Неизвестное происхождение старой записи — JSON `null`, а не значение по умолчанию
`new`. Установка новой коллекции сама не переписывает паспорта: поле появляется при следующем
вызове роли. Старый паспорт без поля читающая сторона может считать равным `origin: null`.
Формула пути, секрет, фрагмент nginx и значения остальных полей не зависят от `origin`.

Закрытый список профилей (`site_passport_profiles`) ведёт владелец учёта; свои коды в проекте не
добавляют, а запрашивают у него.

## Как стыковать с проектом

Проект вызывает роль в своей выкатке, передав переменные из инвентаря, а в генераторе вхостов
добавляет в `server`-блок:

```nginx
include /etc/nginx/snippets/krot-passport-<домен>.conf;
```

Имя фрагмента строится по тому же домену, что и путь (нижний регистр, без `www`). Отсутствующий
фрагмент `nginx` не прощает: `include` на несуществующий файл валит всю конфигурацию, то есть все
сайты машины. Поэтому генератор включает фрагмент только для сайта, у которого роль уже отработала,
а роль в выкатке идёт **раньше** генерации вхостов.

Фрагмент выключает `auth_basic` на этом пути: сайт, ещё закрытый паролем, остаётся читаемым для
учёта. Файл секретов не содержит, замок — путь.

## Что кусается

⚠️ **Путь зависит от секрета.** Смена секрета меняет путь у всех сайтов сразу; роль при следующем
прогоне пишет файл по новому пути, перезагружает `nginx` и только потом удаляет файл по старому; неудачный
`nginx -t` останавливает прогон, и старый паспорт продолжает отвечать. Читающая сторона должна получить
новый секрет до этого.

⚠️ **После упавшего `nginx -t` сперва починить конфигурацию и перезагрузить `nginx` руками, затем
повторять роль.** Перезагрузку вызывает только изменение фрагмента, а в повторном прогоне он уже
записан: роль удалит старый паспорт без перезагрузки, и `nginx`, оставшийся на прежней конфигурации,
ответит по старому пути 404, а новый путь ещё не будет знать.

⚠️ **Хеш — тот же замок, что и секрет.** Фрагмент закрыт по правам (`0640`), каталоги не листаются
(`0711`), поэтому имя файла не узнать, хотя сам файл читаем (`0644`). Задачи, где есть путь, идут с
`no_log`: путь не должен попадать ни в журнал прогона, ни в `ansible -v`.

⚠️ **Общего следа между сайтами нет, кроме формулы**: ни общего пути, ни заголовка, ни строки в
HTML. Журнал доступа по этому пути выключен. Любой другой путь отвечает ровно как прежде —
сценарий molecule сравнивает вхост с фрагментом и без него по статусу, заголовкам и телу.

## Как проверить

```bash
molecule test -s site_passport
```

Сценарий считает путь независимым `hashlib` и сверяет с ним файл, читает ответ `nginx` байт в байт,
проверяет строки `new`/`drop`, явный `null` и отсутствие параметра,
отклоняет неверные значения и типы без изменения прежних файлов. Среди прежних отказов `assert` —
домен вида `../../../etc/nginx` и слишком короткий секрет. В выводе каждого отказа сценарий ищет свой
основной секрет и не находит его; сообщение `assert` секрета не содержит ни в одном случае.
Сравнивает ответы на `/`, `/nope`,
`/robots.txt` и два соседних пути на вхостах с фрагментом и без. Контрольный вектор формулы,
к которому сверяются читающие стороны: для строки секрета `test-secret` и домена `example.test` путь равен
`d095d4ec8c25998e`. Сценарий molecule берёт другое, достаточно длинное значение, потому что роль
короткий секрет не принимает.

Перед включением на живом сайте: ответы на главную, несуществующий путь и `/robots.txt` до и после
совпадают (проверку делает `stemma`, а где её нет, — сравнение `curl -i` без заголовка `Date`).
