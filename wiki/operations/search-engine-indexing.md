# Ночная отправка страниц поисковикам

Роль `indexing` ставит программу `krot-index` и по юниту `krot-index-<проект>-<движок>` на
каждую пару: за ночь программа читает sitemap каждого сайта проекта по HTTP, отбирает страницы
по правилам движка, отдаёт их Google, Bing, Яндексу или IndexNow и пишет итог в схему
`krot_index` базы проекта. Нормы и грабли движков унаследованы целиком от прежней PHP-реализации — их источник и причины в
`design.md` change `2026-09-29-offer-pages-to-search-engines`.

## Что проект объявляет

`indexing_projects` в инвентаре, по ключу на проект (форма — `roles/indexing/defaults/main.yml`):
база, роль приложения `reader`, **явный** список `engines`, ключ каждого объявленного движка и
сайты с адресом sitemap.

- **Движки — список, а не наличие ключа.** Пустой lookup выключал бы движок молча, и ночь шла бы
  зелёной; здесь объявленный движок без ключа — отказ роли.
- **Один ключ — один проект.** Норма Google — Cloud-проекта сервисного аккаунта, норма Bing —
  ключа; роль сверяет `client_email`, ключ Bing и токен Яндекса между проектами машины.
- **Имя проекта — `[a-z0-9]+`**: оно читается обратно из имени юнита.

## Где что на машине

| Что | Где |
|---|---|
| программа | `/usr/local/lib/krot-index/krot_index/` |
| конфиг проекта (без ключей, читают все) | `/etc/krot-index/<проект>.json` |
| ключи (0600, `krot_index`) | `/etc/krot-index/<проект>.env`, ключ Google — `<проект>.google.json` |
| состояние | схема `krot_index` в базе проекта: `page_index`, `index_run`, `index_count`, `schema_version` |

Ключ Google — отдельным файлом, а в env-файле только путь: JSON сервисного аккаунта
многострочный, и `EnvironmentFile=` разобрал бы его по своим правилам.

## Схема в базе проекта

Схему создаёт и обновляет **только роль**, программа лишь сверяет версию и при расхождении
краснеет. Молча заведённая пустая схема на пересозданной базе забыла бы отправленное и потратила
бы норму на повторы — зелёным.

- Программа ходит учёткой `krot_index` по peer-сокету, без пароля; роль проверяет строку
  `pg_hba.conf`, а не предполагает её.
- Таблицы принадлежат `krot_index`: `schema.sql` применяется от её имени и только когда версия
  в базе не та, что в роли.
- `reader` получает `CONNECT` на базу (на случай, если у PUBLIC он отозван), `USAGE` и
  `SELECT`, а через `ALTER DEFAULT PRIVILEGES` — и на таблицы следующих версий. Писать
  приложение не может.
- **Чужую схему `krot_index` роль не перенимает.** Есть схема с этим именем другого владельца —
  отказ до изменений: `schema.sql` пошёл бы по таблицам, которых роль не писала.
- ⚠️ **До 7.0.0 схема называлась `krot`.** Первый прогон 7.x переименовывает `krot`, принадлежащую
  `krot_index`, в `krot_index` (`ALTER SCHEMA … RENAME`): строки, гранты `reader` и права по
  умолчанию переезжают вместе со схемой. Есть обе схемы учётки — отказ до изменений: какая из
  них с историей, решает человек. Чужая `krot` роли не касается.
- **Перед переименованием роль ждёт уже идущие ночи проекта** (`krot-index-<проект>-*.service`
  в `activating`/`active`/`deactivating`), не дольше самой длинной ночи из `indexing_timeouts` плюс 5 мин. Ночь 6.x
  пишет в `krot.*` по имени, и переименование под ней оставило бы отправленные страницы
  незаписанными. Не останавливает: оборванная ночь теряет больше. Не дождалась — отказ с именами
  юнитов, схема не тронута. Ночи 7.x опрос от 6.x не отличает, поэтому обновление — прогон днём:
  ночью ожидание может упереться в предел, стоя за ночами, стыкующимися одна за другой.
- **Программа читает старое имя, пока базу не переименовали** (`search_path krot_index, krot`).
  Программа одна на машину, а базу другого проекта переименует только прогон этого проекта —
  между ними его ночи идут по `krot`.
- **Экраны проекта ломаются в момент прогона, переименовавшего их базу**, а не при выкатке их
  кода. Выкатить их можно заранее: запросы без схемы под `SET search_path TO krot_index, krot`
  читают обе.
- `--check` на машине 6.x показывает переименование (модуль выполняет его и откатывает), но не
  гранты: схемы под новым именем в нём ещё нет.
- Все проверки — база, `reader`, чужая схема, строка peer — идут по всем проектам **до первой
  правки**; отказ по второму проекту не оставляет первый наполовину заведённым.
- ⚠️ **Doctrine проекта должен схему не видеть**: `schema_filter` с исключением
  `krot(_\w+)?\.` — иначе `doctrine:schema:update` предложит её удалить.

## Версия схемы: ночи терпят прежнюю, числа требуют новую

Версия схемы — 2 (в 1 не было `index_count`). Программа на машине одна, а базу каждого проекта
поднимает его собственный прогон роли, поэтому между обновлением программы и прогоном базы
проекта версия в ней остаётся 1. **Ночи отправки принимают 1 и 2** — таблицы, которой у них нет,
они не трогают, и красить их из-за чужого обновления нечем. **Сбор чисел требует 2** и до прогона
роли красен с просьбой его сделать. Версию больше, чем знает программа, не принимает никто.

## Числа индекса — `krot_index.index_count`

Раз в сутки юнит `krot-index-<проект>-counts` читает у Bing и Яндекса, сколько страниц движок
держит у каждого сайта проекта, и пишет по строке на сайт, движок и день. Он нужен проекту,
объявившему `bing` или `yandex`; ключи те же, что у отправки, отдельных не заводится. Юнит свой, а
не шаг ночи отправки, по двум причинам: чтение не тратит норму, и красный сбор чисел не должен
красить ночь отправки (и наоборот), а у ночей свои часы и свои пределы времени.

| Колонка | Смысл |
|---|---|
| `site`, `engine` (`yandex`/`bing`), `day` | ключ; день датирует сам движок |
| `in_index` | страниц в индексе (Bing) / в поиске (Яндекс) на этот день |
| `not_in_index` | исключённых; NULL, если движок числа не даёт |
| `collected_at` | когда строку записали или перечитали |

**NULL — неизвестно, 0 — измеренный ноль.** Повторный сбор перезаписывает день; число, которого
движок в этот раз не назвал, прежнего не затирает (NULL не стирает известное, ноль — заменяет).
Читатель проекта получает `SELECT` на таблицу правами по умолчанию, писать не может. Права
читателя из другого проекта выдаёт тот проект.

- **Bing** — `GetCrawlStats`, поле `InIndex`. Один запрос про сайт целиком отвечает сразу за
  ~месяц; роль каждую ночь пишет весь полученный ряд, то есть поздние поправки Bing перекрывают
  прежние. Дни датирует Bing с отставанием на сутки-двое. «Не в индексе» Bing не даёт никак —
  всегда NULL. ⚠️ Первые дни ряда у молодого сайта — нули: это слова Bing о времени, когда сайта
  в индексе ещё не было, а не наш замер, и настоящий ноль от них не отличить. Прирост считать
  за короткий срок от последнего дня, а не по краям ряда. День без читаемой даты или числа
  пропускается, а не пишется нулём. Метод читает только статистику и не упирается в
  `ThrottleHost`/`ThrottleUser` постраничного `GetUrlInfo`.
- **Яндекс, «в индексе»** — `search-urls/in-search/history`: страницы в поиске. Это не по точке
  в день, а точки на даты обновления выдачи (в снимке ответа проекта за две недели сентября — восемь точек
  с шагом в день-два, не ежедневно), и день берётся
  по дате точки в её часовом поясе. Дней между точками в таблице нет: ничего не достраивается, а
  график между ними соединяет читатель. Две точки одного дня — побеждает последняя. Окно запроса —
  35 суток каждую ночь.
- **Яндекс, «не в индексе»** — только текущее `excluded_pages_count` из `summary`: истории
  остатка исключённых API не даёт (`search-urls/events/history` — потоки «появилось» и «исключено»
  за день, и остаток из них не получить). Число пишется на день сбора (по часам машины), прежние
  дни остаются NULL: история копится с первой ночи роли и не выдумывается назад. Число читается в
  своё время, а точка «в индексе» стоит на дату обновления выдачи — на одной строке они не
  обязаны описывать один и тот же срез.
- **Дата `date_to` у Яндекса — завтра по часам машины:** он датирует точки по московскому времени,
  которое впереди машины на UTC, и точка «сегодня» там иначе выпала бы из окна. Формат даты
  запроса (`YYYY-MM-DD`) взят по аналогии с проверенным разделом статистики запросов Яндекса;
  ⚠️ живым вызовом этого конкретного метода на момент записи не подтверждён (с машины разработки
  хост API недоступен) — первое, что смотреть после применения роли: `journalctl` юнита counts.
- **`HOST_NOT_LOADED` и `HOST_NOT_INDEXED`** у Яндекса — «данных пока нет» у сайта, который он
  ещё не обошёл: строка не пишется, юнит зелёный. Красят юнит: ключ, аккаунт без сайта, ответ
  движка, который не удалось прочитать, отказ записи строки — по сайту, остальные сайты читаются
  дальше. Троттлинг чтения (коды 2, 4, 5 у Bing, 429 у Яндекса) сам проходит: юнит зелёный, сайт перечитается
  завтра. Сбой `summary` Яндекса после успешной истории не теряет историю: точки пишутся, сайт
  остаётся красным. Ответ Яндекса 200 без списка точек, без числа исключённых или с точками, ни одну из
  которых нельзя прочесть, — отказ, а не «данных нет»: сменившаяся форма ответа иначе тихо
  оставила бы юнит зелёным без единой записанной строки. Настоящий пустой список (`[]`) — молодой
  сайт, красить нечем. Дата Bing вне календаря или с несуществующим сдвигом пропускается так же,
  как нечитаемая.

Ночь отправки и сбор чисел друг на друга не влияют: `index_run` по-прежнему про то, что отправлено,
`index_count` — про то, что движок у себя держит; вычитать одно из другого нельзя.

```bash
journalctl -u krot-index-<проект>-counts -n 50
sudo -u postgres psql -d <база> -c "SELECT * FROM krot_index.index_count ORDER BY day DESC, site, engine LIMIT 20"
```

## Снятие: только своё

⚠️ **Каждый проект применяет роль из своего инвентаря, а машина одна** — у каждого проекта в
`indexing_projects` только он сам. Поэтому прогон снимает лишь то, что
знает:

- движок, выпавший из `engines` проекта **этого** прогона, — его юнит уходит;
- проект целиком — **только по имени в `indexing_retired_projects`**: его юниты и три файла.

Проект, которого прогон просто не знает, остаётся: это может быть чужой проект, и его ночи
перестали бы идти без красного — упавшего юнита не было бы, его не было бы вовсе. Цена правила —
проект, выпавший из инвентаря молча, стоит на машине, пока его не назовут в списке снятия.

Схема и строки снятого проекта остаются в его базе — это его история. В `/etc/krot-index` роль
трогает только файлы трёх своих имён (`<проект>.json`, `.env`, `.google.json`) — положенное
туда кем-то ещё остаётся.

## Разведка `--check`

`--check` на машине, где роли ещё не было, проходит и показывает, что роль сделает. Чего в нём
не видно:

- выдачи прав учётке `krot_index` и на схему `krot_index`, пока их **на самом деле** нет в кластере
  (спрошено запросом, а не выведено из `changed`) — видно по задачам, которые их создают.
  `CONNECT` для `reader` выдаётся той же задачей, что и `krot_index`, и без учётки не виден тоже;
- включения и перезапуска таймера, пока его файла нет на диске — видно по задаче файлов юнитов;
- применения `schema.sql` — его `--check` не выполнял никогда.

На машине, где роль уже стоит, `--check` проверяет права и таймеры, как прежде, — в том числе
недоведённые прошлым прогоном. Предпроверки (база, `reader`, чужая схема, peer) идут
по-настоящему. Держит это шаг `check` сценария molecule `indexing` — на чистом контейнере, до
`converge`.

## Как смотреть

```bash
systemctl list-timers 'krot-index-*'
journalctl -u krot-index-<проект>-<движок> -n 50
sudo -u postgres psql -d <база> -c "SELECT * FROM krot_index.index_run ORDER BY day DESC, site LIMIT 20"
```

Каждая строка вывода называет движок и сайт. **Красный юнит значит «чинить»**: ключ, владение,
схема, непрочитанный sitemap, ночь, где не принято ничего без названной причины. Кончившаяся
норма и заглушение — зелёные: красный, повторяющийся от календаря, перестают читать.

Владение у Google — уровень `siteOwner` ключа проекта на `sc-domain:<сайт>`: без него URL
Inspection отвечает 403 `PERMISSION_DENIED: You do not own this site` (проба проекта-потребителя
22.10.2026). Запуск с 11.0.0 его обеспечивает; у сайтов,
запущенных раньше, дыры находит плейбук `search_console_access`
([Запустить сайт](../runbooks/launch-a-site.md#проверить-уже-запущенные-сайты)).

**Непрочитанный sitemap называет причину** (с 11.0.1): `could not read the sitemap: <адрес>
answered 404`, `… is not XML`, `GET <адрес>: timed out (asked twice)` и так далее — адрес без
query string. До 11.0.1 строка была одна на все случаи, и обрыв от сломанного sitemap отличали
только по логу nginx сайта. Отказ одного сайта красит юнит, но ночь идёт дальше: остальные
сайты проекта отправляются.

Файл sitemap, на который никто не ответил (`web.Unreachable`: таймаут, сброс соединения, DNS),
читается второй раз сразу; статус и ответ «не XML» — ответ сайта, их не повторяют. Причина —
замер проекта-потребителя с 29.09 по 22.10.2026: шестнадцать непрочитанных sitemap у двух
движков, каждый раз на другом сайте; в девяти из четырнадцати случаев, где лог nginx сохранился,
отказ пришёл через 61–67 с после того, как origin отдал файл с 200 (таймаут сокета за
Cloudflare); два отдельных прохода по всем сайтам прочитали все за 0,4–8 с. Цена повтора — до ещё одного
таймаута сокета (60 с) на сайт с обрывом; лимиты юнитов (`indexing_timeouts`) это вмещают, пока
обрывается не вся сеть разом. Вывод юнита небуферизован (`PYTHONUNBUFFERED=1`), поэтому время
строк stdout в журнале настоящее, а не секунда выхода программы.

⚠️ **Новый ключ IndexNow в первую отправку получает 403 при исправном файле** (замер
2026-09-29: все три сайта нового проекта, файл забран поисковиком через секунду после POST,
тот же POST минутой позже принят). Программа сперва читает файл-ключ сама, и 403 после верного
файла повторяет один раз через минуту; красный — только если откажут и второй раз. Пауз не
больше десяти за прогон (таймаут юнита IndexNow — час): сайтов с новыми ключами больше — у
остальных ночь «не принято», и ключ уходит снова следующей ночью.

## Соседство с проектами, отправляющими сами

Проект, который пока отправляет сам, делает это своими `krot-index-<движок>` от роли `cron`. Имена похожи, но роль
`indexing` снимает только юниты со своим маркером (`# krot-indexing-unit`), а `cron` — только
со своим. Перевод такого проекта — по порядку из `proposal.md` change: снять старый таймер движка, потом
завести схему и перенести историю, и только потом объявить движок здесь.
