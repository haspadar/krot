# Docker на хосте matilda

Роль ставит Docker с compose-плагином из репозитория Docker и **на этом останавливается**.
Приложение matilda разворачивается своим `compose.yaml`, а не Ansible: тяжёлое специфичное
окружение (playwright, flaresolverr, minio, postgres, php, api) уже воспроизводимо compose'ом, и
второй системе выкатки поверх него взяться неоткуда.

Отсюда и весь набор ролей matilda: `common + docker + firewall + fail2ban`. Голый хост под
Compose — [почему так](../domains/collection-layout.md).

## Членство в группе `docker` — это root

`docker_users` по умолчанию содержит только операторский аккаунт, и это не перестраховка:
членство в группе `docker` **эквивалентно root на хосте** — сокет демона позволяет примонтировать
любой каталог в контейнер и выйти из него с полными правами.

Добавление сюда сервисного пользователя ради удобства снимает всю границу, которую ставят
`bootstrap` и `sudo`.

## Логи контейнеров ограничены по умолчанию

```yaml
docker_log_max_size: 100m
docker_log_max_file: 3
```

Пишется в `/etc/docker/daemon.json`. Без этого json-драйвер растёт неограниченно, и на
долгоживущем донорском хосте диск кончается раньше, чем кто-нибудь посмотрит на логи.

Это тот же класс отказа, что и остальные на странице [отказов](silent-failures.md): ничего не
падает, пока не кончается место, — а тогда падает всё сразу и по причине, не связанной с
виновником.

**Смена этих значений действует только на новые контейнеры.** Существующим она ничего не меняет:
драйвер логирования фиксируется при создании. После правки — пересоздать (`docker compose up -d
--force-recreate`), а не перезапустить.

## Что роль не делает

Не ставит compose-файлы, не заводит сети и тома проекта, не запускает стек. Всё это —
`compose.yaml` matilda. Роль знает про хост, но не про приложения на нём.
