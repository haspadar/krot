# Тесты ролей

Роли проверяются Molecule: сценарий на роль в `molecule/<имя>/`. Каждый поднимает контейнер с
systemd, прогоняет роль, прогоняет её второй раз ради идемпотентности и читает машину обратно.

```bash
molecule test --all          # все сценарии подряд; CI гоняет их параллельно
molecule test -s php         # один сценарий
molecule converge -s php     # прогнать роль и оставить контейнер
molecule verify -s php       # погонять проверки по нему ещё раз
molecule destroy -s php      # убрать за собой
```

Быстрая петля при написании сценария — `converge` один раз, дальше `verify` сколько нужно.
`test` всегда уничтожает контейнер в конце, **отменённый прогон — нет**: после Ctrl-C убирать
`molecule destroy -s <имя>` или `docker rm -f krot-<имя>`.

На macOS нужен запущенный Colima; `colima start` — обычное лекарство, когда `create` жалуется на
сокет.

## Сценарий стоит ровно того, что он ловит

Каждый сценарий здесь проверен **поломкой роли**, которую он покрывает. Верный сценарий держит
`converge` и `idempotence` зелёными, а краснеет на `verify` — это единственная расстановка,
доказывающая, что проверки читают машину, а не отчёт Ansible.

Без этого шага зелёный CI не значит ничего. Замерено: три дефекта ролей и шесть дефектов
в самих проверках найдены именно так, и ни один — чтением кода.

## Начинать с реалистичного исходного состояния

Самая частая ошибка здесь — сценарий с чистой машины. Роль чинит состояние, которого в свежем
контейнере нет, поэтому её задача становится пустой операцией, и удаление этой задачи ничего не
ломает.

Замеренные случаи:

| Сценарий | Что было пропущено | Чем лечится в `prepare` |
|---|---|---|
| `firewall_cloudflare` | задачи «закрыть 80/443» удалялись без последствий: на машине, которая никогда не была открыта, закрывать нечего | сперва открыть порты — и по номеру, и через профиль `Nginx Full` |
| `postgresql` | `restart` не отличался от `reload`: на первой установке сервер стартует уже с готовым конфигом | поднять кластер **до** роли и положить другое значение postmaster-настройки |
| `common` | задачу установки пакета можно было удалить — `prepare` ставил его сам | не ставить; пусть наличие пакета будет фактом о роли |

Общее правило: **если `prepare` уже привёл машину в целевое состояние, соответствующая задача
роли не проверяется ничем.**

## Значения в сценарии не должны совпадать с умолчаниями

Роль с дефолтными значениями часто оставляет файл ровно таким, каким он был. Тогда проверка
проходит и на машине, где роль не запускалась.

- `nginx`: пакет кладёт `rotate 14`, и это же — умолчание роли. Сценарий просит 21.
- `postgresql`: `max_connections` по умолчанию 100 и у роли, и у PostgreSQL. Сценарий просит 123.
- `fail2ban`: `firewall_ssh_port` приходит из **другой** роли через `| default(22)`. При 22
  сломанная ссылка неотличима от рабочей, поэтому сценарий ставит 2222.

## Спрашивать демон, а не файловую систему

Записанный файл и действующая настройка — разные факты, и проверять надо второй.

| Роль | Чем читается | Почему не файлом |
|---|---|---|
| `postgresql` | `select … from pg_settings` | reload на postmaster-настройке молча оставляет старое значение — файл говорит одно, сервер работает по другому |
| `php` | `php -r 'ini_get(...)'`, `php-fpm -i` | у `conf.d` есть порядок загрузки: файл может быть записан и перекрыт |
| `fail2ban` | `fail2ban-client get …` | jail с битым именем фильтра молча пропадает из демона, оставаясь в `jail.local` |
| `common` | `apt-config dump` | apt разбирает весь каталог по порядку; собственный файл роли не ответ |
| `nginx` | `nginx -T` c привязкой к началу строки | вывод печатает файлы дословно, **включая комментарии** — подстрока `server_tokens off` нашлась в закомментированной строке нетронутого пакетного конфига |

## Что в контейнере не так, как на машине

Различие стоит проверять по манифесту Ubuntu, а не додумывать: пакет, которого нет в минимальном
образе, выглядит ровно как забытая зависимость роли. На этом уже один раз был сделан неверный
вывод про `curl` — он входит в Ubuntu 24.04, нет его только в Docker-образе.

- **`curl`, `logrotate`, `python3-debian`, `ca-certificates`** — есть на машине, нет в образе;
  ставятся в `prepare`.
- **`/etc/hostname` и `/etc/hosts` — bind-маунты Docker.** Заменить их переименованием нельзя,
  поэтому `hostnamectl` и `lineinfile` падают с `Device or resource busy`. Сценарий `common`
  снимает маунты в `prepare`, после чего роль работает как на настоящей машине.
- **ufw, nginx и PostgreSQL 18 работают в privileged-контейнере по-настоящему** — проверено, а не
  предположено.

## Две ловушки, из-за которых проверка сервиса ничего не значит

Обе замерены, обе оставляли задачу роли непроверенной:

1. **Пакет сам включает юнит.** После `apt-get install php8.5-fpm` `is-enabled` уже говорит
   `enabled` — значит эта проверка про пакет, а не про роль.
2. **`ansible.builtin.service: state=reloaded` запускает остановленный сервис** (`changed=true`,
   затем `is-active=active`), в отличие от `systemctl reload`, который отвечает
   `is not active, cannot reload`. То есть хендлер поднимает сервис вместо задачи.

Вместе они делали задачу `Enable` в `php` и `fail2ban` удаляемой без покраснения. Лечится в
сценарии: пресет systemd `disable` в `prepare` заставляет dpkg не трогать юнит, и тогда `enabled`
в `verify` может взяться только от роли. Подробнее про этот класс отказов —
[отказы, которые не видно](silent-failures.md).

## Сравнивать точно, а не подстрокой

`failed_when: value not in stdout` — не проверка: `maxretry = 30` удовлетворяет ожиданию `3`,
`72000` — ожиданию `7200`. Замерено в `fail2ban`, где из-за этого заявленная строгость
(«все значения отличаются от умолчаний») почти ничего не стоила. Сравнивать
`stdout | trim != value`; для многострочного вывода — привязывать к границе строки.

## Что покрыто и чем это считается

```bash
python3 scripts/coverage.py
```

Печатает, у каких ролей есть сценарий, и **валится**, если роль не названа ни в одном списке:
непоименованная роль читается как проверенная, хотя её не проверяет ничто. Там же пол покрытия —
скрипт падает при снижении, но поднимается пол только руками, коммитом.

Считается охват, а не покрытие кода: Molecule такого механизма не имеет, а `ansible-test coverage`
меряет Python модулей и плагинов, которых у krot нет.

Роли без сценария перечислены в самом скрипте с причиной — `bootstrap` (Molecule ходит мимо sshd,
и сломанный конфиг sshd прошёл бы незамеченным — зелёный ровно в том случае, ради которого роль
существует), `deploy` (работает с control-машины), `deploy_keys` (нужны настоящие приватные
репозитории), `docker` (ставил бы Docker внутрь контейнера).

## CI

`.github/workflows/lint.yml` держит сценарии отдельно от линтеров, чтобы красная роль отличалась
от красного линтера с одного взгляда. Оба — `lint` и `molecule` — входят в обязательные проверки
`main` (`enforce_admins: true`, обойти нельзя и владельцу).

**Сценарий на job, а не `--all` в одном.** Прогон 2026-08-16 замерен по маркерам
`[<сценарий> > <действие>]` в логе: девять сценариев, **783 секунды суммой**, самый долгий
`firewall_cloudflare` — 136 с, самый быстрый `fail2ban` — 61 с. Последовательно это 14 минут
ожидания, по job'у на сценарий — примерно максимум из них. Машинное время то же самое; перестаёт
ждать человек, а на публичном репозитории эти минуты бесплатны.

Список сценариев CI **читает из `molecule/`**, а не хранит в workflow. Список руками правится
дважды при добавлении сценария, и забывается именно копия в CI — а пропавший сценарий выглядит
точно как проходящий.

### Матрица и обязательная проверка — отдельные имена

Матрица отчитывается **по чеку на ногу**: `molecule (php)`, `molecule (nginx)` и так далее. Чека с
именем `molecule` при этом не существует, а обязательная проверка, которая никогда не приходит,
блокирует все PR навсегда.

Поэтому ноги называются `molecule-scenario`, а имя `molecule` держит отдельный job-агрегатор — он
и есть обязательная проверка. Переименовывать любой из двух — только вместе с правкой защиты
ветки.

У агрегатора `if: always()` и явная проверка результатов, а не одни `needs`. Причина в том, как
устроен пропуск: **упавший `needs` не красит зависимый job, а пропускает его**, а пропущенная
обязательная проверка — не красная, GitHub ждёт её бесконечно. То же самое даёт отменённый прогон,
который `concurrency` устраивает при каждом втором пуше. Отдельно отвергается `skipped` у самой
матрицы: пустой список сценариев иначе прошёл бы гейт, не прогнав ни одного.

Проверено фактом, а не настройкой: PR с зелёным `lint` и красным `molecule` получает отказ «the
base branch policy prohibits the merge» при `mergeable=MERGEABLE`.
