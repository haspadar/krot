# Регистрация GA4

GA4 снова поддерживается общими модулями коллекции. Проект включает
`site_analytics.ga4: true` при запуске нового сайта и сохраняет результат своим
`site_results_writer`. Коллекция не вставляет скрипт в HTML, не ведёт конфиг приложения
и не включает GA4 молча для потребителя, который его не запросил.

## Человек и технические ключи

`site_ga4_owner_email` — явный человеческий владелец этого домена в Search Console,
взятый потребителем из своего проверенного реестра. Он также должен быть в
`site_search_console_owners`. Общего владельца по умолчанию нет.
`site_ga4_account_id` — отдельный обязательный числовой ID Analytics account.
До любой записи Analytics модуль читает все страницы `accounts/{ID}/accessBindings`
и требует для этого человека `predefinedRoles/admin`. Если список недоступен или
человека там нет, запуск останавливается с причиной API. Выдача прав человеку
после создания свойства не заменяет доказательство принадлежности аккаунта.
Групповое или косвенное администрирование не считается доказанным этим контрактом:
нужна явно читаемая запись человека в account bindings.

`site_google_service_account` — JSON ключ запуска: ему нужны права администратора
на выбранном Analytics account и доступ Site Verification для домена. Он создаёт
свойство в человеческом аккаунте, а не изображает человеческую OAuth-сессию.
Analytics Admin API должен быть включён в его Cloud project.
`site_ga4_reader_service_account` — отдельный явный параметр JSON ключа сбора.
Он может совпадать с ключом запуска: важны назначение и проверенный доступ,
а не создание нового principal. Ему нужен включённый Analytics Data API. Существующий ключ допустим;
роль не понижает его уже выданные права и не создаёт новый ключ.

Перед GA4 роль подтверждает GSC-владение. У нового сайта это делается через TXT
и Site Verification до передачи ID приложению; отправка sitemap остаётся после
открытия сайта. При уже подтверждённом владении повторная регистрация счётчика
не требует изменения DNS. В check mode отсутствующий GSC resource нового домена
показывает pending, но проверка человеческого администратора Analytics account
всё равно обязательна. В apply отсутствие подтверждённого владельца — отказ.

## Повторный запуск без второго свойства

`site_ga4_property_id` и `site_ga4_stream_id` — необязательные числовые ID для точного
выбора старых ресурсов. Stream ID требует property ID; оба проверяются, а не
подменяются новым ресурсом при 403, 404 или несовпадении домена.

Без property ID модуль читает все страницы свойств указанного аккаунта и их потоков.
Свойство подходит по displayName, равному домену, либо по web stream с URL домена
(вариант www также допустим). Два свойства — отказ с просьбой указать ID.
Внутри свойства выбирается поток с совпадающим доменом в `defaultUri`, а не первый
попавшийся web stream. Несколько совпадений требуют stream ID.
Незавершённое свойство без нужного потока получает поток в том же свойстве.
Переименованное свойство с правильным URL также переиспользуется.

Новые свойства создаются с Europe/Berlin и EUR. Существующим свойствам модуль
никогда не меняет timezone, валюту или имя: повторная регистрация не является
миграцией исторических данных. Ошибка списка, невалидный ответ и отказ API не
трактуются как отсутствие ресурса. Ответ каждой записи сверяется отдельным чтением.
Одновременные запуски регистрации одного домена должен исключать потребитель:
у API создания нет атомарного уникального ключа по домену.

## Reader и результат

`ga4_access` сначала читает минимальный Data API report ключом читателя. Если он
уже доступен, ничего не выдаётся. Только отказ Google о недостаточных правах
разрешает выдать `predefinedRoles/viewer` на одном свойстве, затем чтение повторяется
до подтверждения. Отключённый API, квота и ограничение ключа приводят к отказу с
исходной причиной, а не к попытке лечить их выдачей роли.

`site_analytics_results` содержит `ga4_account_id`, `ga4_owner_email`,
`ga4_property_id`, `ga4_stream_id`, `ga4_measurement_id`, `ga4_timezone`.
После проверки тега потребитель публикует назначение через
`site_passport_google_analytics` — [контракт паспорта](site-passport.md).
Это штатный путь обнаружения GA4 читателем паспортов, без отдельного реестра в коллекции.

ID пусты, если check mode лишь планирует создание; проектный writer в check mode
не вызывается. Список остальных переменных — в defaults роли `site`.

Для восстановления существующих сайтов достаточно вызвать локальные модули
`haspadar.krot.ga4_property` и `haspadar.krot.ga4_access` последовательно с теми же
явными параметрами. Машинный playbook и полный запуск сайта для этого не нужны.
Модули не обращаются к серверу сайта и не меняют его конфигурацию.

```yaml
- name: Register the property in its human account
  haspadar.krot.ga4_property:
    domain: "{{ site_domain }}"
    account_id: "{{ site_ga4_account_id }}"
    owner_email: "{{ site_ga4_owner_email }}"
    service_account: "{{ site_google_service_account }}"
    property_id: "{{ site_ga4_property_id | default('') }}"
    stream_id: "{{ site_ga4_stream_id | default('') }}"
  register: ga4
  delegate_to: localhost
  become: false

- name: Prove reader access
  haspadar.krot.ga4_access:
    property_id: "{{ ga4.property_id }}"
    service_account: "{{ site_google_service_account }}"
    reader_service_account: "{{ site_ga4_reader_service_account }}"
  when: ga4.property_id | length > 0
  delegate_to: localhost
  become: false
```

## Контрольные сценарии

Юнит-тесты используют HTTP fake с проверкой JWT и scope: отсутствие human admin,
неверный GSC owner и 403 account bindings должны оставить ноль записей.
Повторный запуск сохраняет ID и timezone; прерванное создание добавляет только поток;
пагинация и переименованные свойства не создают дубликаты; неоднозначность требует ID.
Отключённый Data API не выдаёт reader никаких ролей.

Полный `scripts/molecule-fast.py --full site_launch` проверяет новый сайт, сухой
прогон без записей, повтор без изменений, GSC-владельца, один поток и Viewer читателя,
а также все ID, переданные writer. Для живого аккаунта потребитель сначала запускает
check, сверяет владельца, account, найденные ID и timezone, затем apply и повторный
check. Успех fake-сценария не доказывает доступность конкретного production account.
